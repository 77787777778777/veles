*veles 0.2.3, 2026-11-12.*

A small errata release. 0.2.2 was deployed to a fleet of four nodes (two built
from the development tree, a Windows node and a phone on the published
artifacts), and its new deployment-consistency check answered "The fleet is NOT
consistent: 4 node(s) differ" with every node on the release. 0.2.3 makes the
check compare what it should, makes the Android packages say which commit they
were built from, and fixes an IRC reply that carried the bot's own nick in front
of every line.

## Fixes

### Fleet command center

- The consistency verdict (**Drift…**, `/fleet drift`, the Instances detail)
  compares the point release and the commit, not what a platform loads:
  - A module that is not on every node no longer changes the verdict. Racket and
    Lisp are not built for Windows and a phone loads its own set, so 0.2.2's
    "consistent with differences" was the best any real fleet could read. The
    fleet is now "consistent", and each such module is still named with the
    nodes that lack it.
  - A module standing by for a singleton lease (IRC or Telegram on the nodes
    that do not hold the lease) reports no version and is no longer compared.
    0.2.2 flagged the node that ran the module and the one that stood by.
  - A published build and a build of the development tree at the same commit
    are the same build. The public tree is an export with commit ids of its
    own, so a published build's revision matched no development build's. The
    published tree now names the development commit it was exported from
    (`SNAPSHOT_OF`), a build reports it beside its own revision, and the check
    compares that. A node whose build is a snapshot of another commit reads
    `revision <its own> (snapshot of <the other>)`.
  - A build that does not know its source (a build of a modified tree) reads
    "revision not reported" and agrees with nothing. Two such builds used to
    agree with each other.
- A node's row in the drift report (`revision_differs`) follows the same rule,
  so the rows and the verdict do not contradict each other.
- A backup carries the command center's audit trail (`fleet_audit.jsonl`: who
  restarted or reconfigured which node, and the result). 0.2.2 added the file
  and not its entry in the backup set, so `veles backup` left it out and a
  restore lost it.

### Installer and plugins

- Describing a process plugin right after it was written (an install or an
  upgrade) no longer fails with "Text file busy" when the gateway starts
  another child at that moment. The kernel refuses to run a file that anything
  still holds open for writing, and a child forked by another thread holds the
  writer's descriptor until its own exec; `--describe` now waits that window
  out inside its 10 seconds.

### IRC

- A reply in a channel no longer shows the bot's own nick in front of every
  line. A channel turn carries the channel's recent lines as `HH:MM <nick> text`,
  the bot's own among them, and a model that saw a run of its own lines there
  answered in the same shape: `<nick>` in backticks at the start of each line,
  which went out as monospace and read as a second header (after the `name: `
  the gateway puts on a reply when the conversation partner changed). The
  adapter now removes its own speaker tag from a reply that opens with one, and
  the context block says which lines are the bot's own and that an answer is
  plain text. Another nick's tag is a quote and stays.

### Android

- The gateway in the APK reports the commit it was built from. The 0.2.2 APK
  reported `unreported-dirty-build`: only the host package was told its
  revision.

## Building and testing veles

- `scripts/release/export-public.sh` writes `SNAPSHOT_OF` (the full id of the
  exported commit, one line) at the root of the snapshot and refuses to export a
  tree that already tracks one. `crates/veles-frontends/build.rs` stamps it:
  from the file in a plain cargo build, from `VELES_SNAPSHOT_OF` where the flake
  passes it. `scripts/test-export-public.sh` (a precommit step) runs the real
  export and reads the marker back.
- The flake gives the host package and the Android engine one source stamp
  (`sourceStamp`), and `checks.android-source-stamp` fails evaluation when they
  are told different things.
- `scripts/release/check-public-tree.sh <commit>` runs the flake's checks on the
  public snapshot of a commit as a published build sees it: the export is
  committed in a scratch git repository, so the build has a revision of its own
  and the marker. A `path:` export has no revision, and a build that does not
  know its source does not take the paths a published build takes.

## Known limits

- A 0.2.2 node does not name what it was exported from. In a fleet that mixes a
  published 0.2.2 build with a development build, the check flags it by its
  revision, as before.
- A 0.2.3 desktop attached to a 0.2.2 gateway reads that gateway's "consistent
  with differences" as "consistent". A 0.2.2 desktop attached to a 0.2.3
  gateway shows its old sentence ("run the same build, modules and plugins")
  for a consistent fleet, also when a module is not on every node; the modules
  are named below it.
- The check compares two builds by the commit they name. A public commit made by
  hand after an export (a correction to the release notes) keeps the marker of
  the export before it.
- The new sentence in the desktop is machine-translated in 46 locales and
  unreviewed by native speakers, like the rest of the 0.2.2 catalogs.

## What was checked

Checked before the tag:

- The precommit gate on Linux and on the Windows build host, and the hermetic
  `nix flake check`, on the tagged commit.
- Every fix with a test that fails without it, and each behaviour reverted in
  turn to see its test fail: 17 mutants in the Rust code, the flake's
  Android check, the export's refusal to export a snapshot, the backup set
  without the audit trail, and the describe without its wait.
- The consistency verdict on the fleet as 0.2.2 was deployed: the test's four
  nodes carry the modules that fleet reported on 2026-11-11.
- The export run for real into a scratch directory, the marker read back, and
  the flake of the exported tree evaluated: it passes the exported commit to
  the host package and the Android engine.
- The public tree's checks as a published build (`check-public-tree.sh`). A
  first tag was checked on a `path:` export instead; the public repository's CI
  then failed one test that changes only a fingerprint's revision and expects a
  difference, which under one export marker is the same source. The test was
  corrected and the tag moved before anything was published.
- The IRC fix on the text of the reply that showed the fault, through the
  adapter to the wire of a scripted server.
- The desktop's verdict line off-screen, against a current gateway's answer and
  a 0.2.2 gateway's.

Not checked before the tag:

- A fleet of 0.2.3 nodes. The four nodes are upgraded from this release's own
  artifacts and the check is run on them; the result is in the release record.
- The APK's revision on a phone (same: read after the upgrade).
- The IRC fix against a live model.
- A native-speaker review of the new sentence.

## Upgrading

- Run the installer again on Linux or Windows, or install the new APKs over the
  old ones on Android (userland first). The Android version code becomes 10; the
  APKs keep the existing release certificate. Configuration and transcripts are
  preserved. Restart the gateway and reload the desktop.
- Nothing on a wire changes. A fingerprint gains one field (`snapshot_of`), which
  older nodes ignore.
- The SDK crates on crates.io stay at 0.2.0: none of them changed.
