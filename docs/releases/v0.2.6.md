*veles 0.2.6, 2026-11-14.*

One fix, to how the session store writes to the disk. It is what stalled
desktop sessions when the machine was busy, and what ended one-shot chats
beside a running gateway with "database is locked".

## Fixes

### The store no longer waits for the disk while it holds its locks

- Every write to the session store used to wait for its own sync to the
  disk, and it waited holding both SQLite's write lock and the lock the
  whole process shares for the store. On the laptop this was found on, one
  small sync takes 35 to 100 ms with the disk idle and seconds with it busy.
  So whoever wrote made everybody else wait: a desktop session stalled
  behind the gateway's gossip, the gateway's heartbeat and gossip failed
  behind a chat, and a `veles chat -q` beside the gateway gave up after
  SQLite's five-second wait. In one pass of the docs translation, which
  runs three such chats at a time, 28 of 154 logged "database is locked"
  and 15 of them died of it.
- A write is now answered as soon as SQLite has it in its write-ahead log.
  A worker thread syncs the log to the disk straight after, several writes
  to one sync and at most one sync a second when nobody is waiting for it.
  It also folds the log into the database file, which SQLite used to do
  inside the writer's call, and does it less often.
- Measured on that laptop, each pair on the same build with only the
  setting changed and the gateway restarted:

  | | sync on every write | sync in the background |
  |---|---|---|
  | gateway alone, four minutes: time the store's write lock was held | 3.7 s, 2.9 s at the longest | 0.06 s, 5 ms at the longest |
  | six chats at a time, twice, on a quiet disk: time for the twelve | 31 s | 33 s |
  | the same: time the write lock was held | 1.9 s, 67 ms at the longest | 0.25 s, 15 ms at the longest |
  | the same with three writers keeping the disk syncing: chats that finished | 3 of 12, nine died of "database is locked" | 12 of 12 |
  | the same: time for the twelve | 325 s | 38 s |
  | the same: time the write lock was held | 318 s, 7.3 s at the longest | 5.2 s, 1.9 s at the longest |

  The first row depends on how busy the disk is otherwise: an earlier
  pair, taken while the machine was doing other work, gave 37.5 s against
  0.03 s.
- What is not fixed: a disk that is saturated slows plain writes down too,
  not only syncs. In the last rows the store's write lock was still held
  for a seventh of the time, 1.9 s at the longest. Nothing failed there,
  but a desktop session on such a disk can still feel it.

### What this changes for your data

- If veles crashes, is killed or is restarted, nothing is lost, as before.
- If the machine loses power or is reset, the writes of its last moments
  can be missing afterwards: about a second's worth, more if the disk was
  saturated. Before, a write that had been answered was on the disk. The
  database is never left inconsistent either way.
- Nothing leaves the node before it is on the disk. Before a request goes
  to another node, and before another node is answered, the node waits,
  holding no lock, until everything written to its store so far is synced.
  A peer therefore never holds a row that this node could lose in a power
  cut, which is what the copies the nodes keep of each other's sessions
  depend on. A request that cannot be synced within two minutes is not
  sent.
- A sync that fails is not forgotten. After one, the node sends nothing
  more to its peers and answers them with an error until it is restarted:
  the operating system may have dropped what it could not write, and a
  later sync that succeeds says nothing about it.
- A command ends only after what it wrote has been synced.
- `VELES_STORE_SYNC=full` in the node's `.env` (or the environment) keeps
  the sync on every write; the node still syncs before anything leaves it.
  `veles doctor` says which way the store is running. Memory keeps its own
  sync on every write either way. `docs/install.md` ("When a write to
  `state.db` reaches the disk") and `docs/pool.md` ("What a node tells the
  others is on its disk first") have the details.

### A turn's message waits for a busy store instead of being dropped

- When the store was held by another writer for longer than SQLite's
  five-second wait, the turn logged "persist failed" and went on without
  the message: the session had a hole in it, and a one-shot chat usually
  ended on the same error a moment later. The turn now asks again for up
  to half a minute, in tries of a quarter of a second with the process's
  store lock let go in between, so that the rest of the process can still
  read while it waits. It says in the log how long it waited when that was
  more than a second.
- A message is now written as one transaction. It was two writes, and an
  error on the second left the message in the store and reported failure.
