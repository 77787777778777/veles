*veles 0.2.4, 2026-11-13.*

Two things a bot in a shared channel kept getting wrong, and one tool that
lets it answer questions about itself.

## New

### The agent can read its own documentation and source

- A new tool, `veles_docs`, answers from what is built into the binary: no
  network, no file access, and open to any caller, a guest included.
  - **Pages**: the README, every page of `docs/` and this version's release
    notes. `page=<name>` opens one (its introduction and outline),
    `section=<words of a heading>` one part of it, `query=<words>` searches
    all of them.
  - **Source**: a snapshot of the tree the binary was built from (the crates'
    sources, the desktop's Tcl, the plugins and the deployment files; about
    4 MB compressed). `grep=<text>` finds lines, `file=<path>` opens a file
    (an outline of its definitions when it is long, `lines=a-b` for a range),
    `file=list` shows the tree.
  - **Commands**: a `commands` page built from the table `/help` shows.
- The system prompt says so in one sentence. Before, a person who asked the
  bot how it works got "I don't know" or "I'm sandboxed and can't see my
  source": the prompt said nothing about what veles is made of, and a caller
  who is not the owner works in a sandbox container, where the model went
  looking for the source and did not find it.
- A new page, `docs/channel-tcl.md`: what `tcl …` in a channel runs (the
  sandbox, or slopdrop's persistent interpreter behind the bridge), how to
  look inside it with plain Tcl, how to tell a native command from a proc,
  and what the tree records about where slopdrop's stock commands get their
  data.
- `tcl_eval`'s description now says it is veles' own interpreter and that
  the Tcl a channel's `tcl` commands run is `tcl_state_eval`. A model refused
  the first had not tried the second.

## Fixes

### Who the owner is

- A turn's origin line now says who the owner is on the surface it came
  through, to a caller who is not the owner. A refused owner-only tool told
  the model "tell the user the owner has to run it", nothing said who that
  is, and the model named a bystander (the first nick in the channel's
  list). The name is, in this order:
  - on IRC, the nick in the channel (for a private query, on the network)
    whose hostmask an owner rule matches;
  - the name the owner last spoke under on that surface (any connector; kept
    in memory, so unknown after a restart until they speak);
  - the name `[[acl.users]]` gives the owner as a person;
  - otherwise nobody, and the line says to name nobody.
- The refusals of owner-only tools point at that line.
- Under an ACL that makes unlisted senders owners, or with no ACL at all,
  nothing is said: everybody is the owner there.

## Building and testing veles

- `crates/veles-cli/build.rs` packs the source snapshot (sorted, without
  timestamps, so one tree packs to the same bytes). It lives in the last crate
  built so that an edit elsewhere does not rebuild veles-core.
- `selfdocs.rs` compiles in `docs/releases/v<version>.md`: a version bump
  needs its release notes file in the same commit.
- A test holds the bundled pages to the `docs/` directory, so a new page
  cannot be left out.

## Known limits

- The snapshot is of veles. slopdrop is a separate program; its source is
  not in the binary (the `channel-tcl` page says where it is).
- What the snapshot holds is public in the repository already, deployment
  files included. A bot in a channel will now quote from them when asked.
- The owner's name on a surface without a member list (Telegram, Bluesky) is
  the one they last spoke under since the gateway started.
- The identity prompt grew by one sentence and the core tool list by one
  tool (about 900 bytes of schema).

## What was checked

Checked before the tag:

- The precommit gate on Linux and on the Windows build host, the hermetic
  `nix flake check`, and the public tree's checks as a published build
  (`scripts/release/check-public-tree.sh`), on the tagged commit.
- Every new behaviour with a test that fails without it, and each reverted in
  turn: 27 mutants. Two survived the first pass (the source search was not
  tested with mixed case, and a snapshot damaged after a good record was not
  tested at all); those tests were tightened until they failed.
- The snapshot the build really packs, read back through the tool in the
  binary's own tests: the IRC adapter's source, a deployment file, the tree,
  the command table.
- The owner clause against a member list shaped like the channel's where the
  fault showed.

Not checked before the tag:

- A live model in a channel: whether it reaches for `veles_docs`, and whether
  it now names the owner. Watched after deployment; the result is in the
  release record.
- The snapshot on Android. The APK's source set holds the crates only, so the
  phone's binary carries those and no desktop Tcl, plugins or deployment
  files.
- macOS.

## Upgrading

- Run the installer again on Linux or Windows, or install the new APKs over
  the old ones on Android (userland first). The Android version code becomes
  11; the APKs keep the existing release certificate. Configuration and
  transcripts are preserved. Restart the gateway and reload the desktop.
- Nothing on a wire changes.
- The SDK crates on crates.io stay at 0.2.0: none of them changed.
