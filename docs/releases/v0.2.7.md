*veles 0.2.7, 2026-11-15.*

A crash fix. Five places cut text that came from outside at a fixed number
of bytes, without regard for characters, and in the gateway the cut
aborted the process whenever it fell inside a multi-byte character.

## Fixes

### A cap inside a character no longer aborts the gateway

- When a session's history grows past its budget, veles summarizes the
  older part. The transcript it hands the summarizer is capped, and the
  cap was a byte count cut with `String::truncate`, which panics when the
  byte is inside a character. A panic in the gateway aborts the process
  so that its supervisor restarts it.
- That is what happened on the laptop on 2026-11-14: a long session (1.29
  million characters) whose turn a restart had interrupted was compacted
  when the gateway resumed the turn at start-up, the cap met a character
  of more than one byte, and the gateway aborted at every start until
  turn recovery gave the turn up after six tries. The code was three
  months old; sessions that are mostly ASCII had never put a character
  across the cap.
- Four more caps had the same flaw and are fixed with it:
  - an HTTP body over 1 MB read by a Tcl plugin (`veles::http_get`,
    `veles::http_post`);
  - the output of a shell command spliced into a custom slash command,
    over 4,000 bytes;
  - a program's output from `execute_code`, over 50 KB;
  - a provider's error body over 4 MiB on a streamed call.
- Each now cuts at the character boundary before its cap. Each has a test
  that puts a two-byte character across the cap, and all five failed with
  the gateway's own panic before the change.

### If a turn of yours was given up

A turn that recovery gave up on shows the note "the gateway restarted
while this turn was running, and continuing it failed 6 times". Nothing
was repeated. Send the session a message to continue it.

## Also in this release

Test changes after 0.2.6, none of which changes what veles does: the
worker registry no longer lists a sync worker that has stopped (the first
public CI run of 0.2.6 failed on a test that looked in that moment), and
five tests no longer depend on how fast the machine running them is.
