*veles 0.2.5, 2026-11-13.*

A fix found by putting the 0.2.4 gateway on a real IRC server with a real
model and three scripted people in the channel, and the missing half of
ticketed delegation: an agent can now ask the owner to sign for work it
places on another node.

## New

### An agent can ask for a ticket when it places work on another node

- `delegate_task` takes `raise: true` together with a node name as
  `backend`. The placing node writes a ticket request for exactly that
  delegation (the goal, the context, itself as the origin, the named node as
  the target, the caller's own level as the grant) and puts it to whoever is
  attached to the session and to the headless signers. With the ticket the
  child runs on that node at the granted level, on its host instead of in its
  sandbox. Without one nothing is placed.
- Why nobody was ever asked to sign: the receiving side of this has been
  there since tickets were introduced, and nothing on the asking side built a
  request. A part placed on another node ran at the user level in that node's
  sandbox, was refused whatever needed more, and was told not to look for
  another route. The pool page said a host shell on another node needs a
  ticket; no path an agent could take asked for one.
- A part placed without `raise` that is refused something on the other node
  is now told to say in its result what needed more, and that the agent which
  placed it can ask again with `raise`. A delegated part cannot ask questions,
  so its result is the only way that reaches anybody.
- When no ticket comes back, the answer says so in terms of what this node
  could do: declined or not signed within ten minutes, and, where no headless
  signer is configured, that only a person attached to the session could have
  been asked. It used to say "the owner declined" in every case. The same
  text now answers a call by an identity that holds a role by ticket.
- `raise` needs a named node (`any` and `gpu` pick one at placement, and a
  ticket names one), asks for the caller's own level and never more, and is
  for one delegation, not a `tasks` batch. `docs/pool.md` has the section.

### IRC: a pasted ticket is taken without a mention

- When a call needs a ticket, the bot posts the request in the channel and
  says to paste the signed ticket there. In a channel that requires a
  mention the paste was dropped like any other unaddressed line: the request
  sat out its ten minutes and the call never ran. The same ticket addressed
  to the bot by nick was taken at once. A line that is a pasted ticket now
  reaches the request that waits for it, and who may answer that request is
  checked as before.
- A ticket pasted where no call is waiting for it gets a notice saying so and
  starts nothing. A message that only quotes a ticket in a sentence is
  conversation, as before.

## Fixes

### IRC: the owner is recognised when they are in the channel

- 0.2.4 tells a turn from someone who is not the owner who the owner is on
  that surface ("the owner of this agent is here as …"). On IRC this held
  only for an owner who was in the channel before the bot joined, on a server
  with `userhost-in-names`, and who had not changed nick since. In every other
  case the turn was told that the owner "is not known to be here now", or
  that it is not known under which name they appear, while the owner sat in
  the channel. In a private query the bot then told the asker it could not
  say where to find the owner.
- The cause was the channel's member list. The owner's rules are hostmasks,
  and the list had a hostmask only for the members a `NAMES` reply named with
  one. Someone who joined after the bot was listed as a bare nick, a nick
  change dropped the user and host the entry had, and on a server without
  `userhost-in-names` no entry had them at all.
- The member list now takes the user and host from every place the server
  names them: the prefix of a `JOIN` (which also replaces the mask held for a
  nick that rejoins from another host), each row of the `WHO` reply the bot
  already asks for after `NAMES`, the prefix of a `NICK` line, and the prefix
  of a line someone says in the channel. A nick change keeps the user and
  host.
- What you will see: `irc names` and the `here (N): …` line of the channel
  context a turn reads now show `nick!user@host` for the members of every
  network, as they did before on servers with `userhost-in-names`.

## Building and testing veles

- Tests in four files used hostmasks copied from a live network. They use
  made-up ones now, and the check a tree passes before it is published
  refuses a string shaped like that network's cloak.
- `crates/veles-irc`'s stub server tests gained a helper that runs a server
  script and reads back the member list and the owner's nicks while the
  connection is up (`roster_seen`).

## Known limits

- A signing request is raised for a person in a channel only when their
  `[acl]` rule has a `ticket_role` (`docs/acl.md`, "A role held by ticket").
  Without one a refused call stays refused; that is configuration, and this
  release does not change it.
- A tool call homed on another node asks for a ticket when that node refuses
  the tool at the user level. A `host: true` on such a call is still run in
  the other node's sandbox without asking.
- A node verifies a ticket against its own `[cluster.ticket_signers]`. A node
  with none accepts no ticket, raised delegation included.
- On IRC a ticket request longer than one line is posted as several lines
  and has to be joined before it is signed by hand. The headless signer is
  not affected.
- A host that changes without a rejoin (the `chghost` capability is not
  requested) is picked up at that person's next line in the channel.
- A member list that is full (5,000 entries) learns nothing about the people
  it left out.
- Unchanged from 0.2.4: on a surface without a member list (Telegram,
  Bluesky) the owner's name is the one they last spoke under since the
  gateway started.

## What was checked

Checked before the tag:

- The precommit gate on Linux and on the Windows build host, the hermetic
  `nix flake check`, and the public tree's checks as a published build, on
  the tagged commit.
- Eight new tests, six of them against the stub IRC server (a join after the
  bot, a rejoin from another host, a nick change with and without a known
  mask, `WHO` rows on a server without `userhost-in-names`, a line said in
  the channel). All failed before the change. Ten mutants, one for each part
  of it; each turns at least one test red.
- A gateway built from the tagged tree on a local ergochat, with the model
  the production bot uses and scripted clients as the owner, a bystander and
  an asker: the owner in the channel before the bot, joining after it,
  changing nick, leaving, and asked about in a private query. What each turn
  was told about the owner was read from the gateway's own record of the
  turn.

- The asking side of a raised delegation against the receiving side's own
  check: the request a placing node builds, signed with a test key, is
  accepted by the target for that goal and context and refused for another;
  a decline places nothing; a caller at the user level, a `tasks` batch and a
  backend that names no node are refused before anybody is asked.

- The ticket flow over IRC on the local ergochat, with a throwaway key: a
  caller holding the owner role by ticket asks for an owner-only call, the
  request is posted, signed with `veles ticket sign` and pasted back without
  a mention, and the call runs.

Not checked before the tag:

- A raised delegation between two real nodes with a real signer.
- The two production networks. One has `userhost-in-names` and one does not;
  the stub server tests cover both shapes, the live check ran on a server
  that has it.
- macOS.

## Upgrading

- Run the installer again on Linux or Windows, or install the new APKs over
  the old ones on Android (userland first). The Android version code becomes
  12; the APKs keep the existing release certificate. Configuration and
  transcripts are preserved. Restart the gateway and reload the desktop.
- Nothing on a wire changes.
- The SDK crates on crates.io stay at 0.2.0: none of them changed.
